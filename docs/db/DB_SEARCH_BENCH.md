> 왜: HNSW 없이 "범위로 거른 뒤 정확 계산"이 충분히 빠른지([`DB_DESIGN_WHY.md`](DB_DESIGN_WHY.md) 8절)를 실제 데이터(데이터 버전 1, 검색 대상 224,677곳)로 확인한다.
> 노트북: [`infra/colab/db_search_bench_1.ipynb`](../../infra/colab/db_search_bench_1.ipynb) — Colab VM에 PostgreSQL 16 + PostGIS + pgvector를 깔고 덤프를 복원해 잰다(로컬 PC 발열을 피하려고).

## 지금까지 결론(2026-11-20, 1~3차)

| 회차 | 노트북 | 알게 된 것 |
|---|---|---|
| 1차 | `db_search_bench_1` | 넓은 범위(반경 10km·시도·넓은 화면)가 p95 480~740ms. 원인은 계산이 아니라 `vector(1024)`를 TOAST에서 꺼내는 비용(행당 버퍼 약 9번) |

- **HNSW는 넣지 않는다.** 저장 방식을 바꾸는 것으로 모든 경우가 기준(p95 150ms) 안에 든다.
- 4차를 통과하면 `rr_sorted`를 V1 스키마·적재 코드에 반영하고, 못 하면 `plain_sorted`(fp32만 행 안, 법정동 코드 순)로 간다.
- 동시 부하(초당 20건)는 Colab CPU 2개에서 클라이언트까지 같이 돌아 판단하지 못했다. 운영 서버 사양이 정해지면 따로 잰다.

## 무엇을 재나

평가 질의 695개(AI 레포 `service_queries_v1.csv`: 검색어 + 검색 위치)를 임베딩 모델로 벡터로 만들어, [`DB_TABLES.md`](DB_TABLES.md) 10-1절 쿼리를 그대로 보낸다.

| 경우 | 쿼리 |
|---|---|
| ① 반경 1km / 10km | 검색 중심 원 안 벡터 상위 50 |
| ② 시군구 / 시도 | 검색 위치의 법정동 코드 앞 5 / 2자리 전체에서 상위 50 |
| ③ 지도 도시 화면(약 5×4km) / 넓은 화면(약 27×22km) | 화면 사각형 안 상위 50 |
| ⑤ 검색어 없는 도시 / 넓은 화면 | 화면 안 가까운 순 300 |

| 동시 부하 | 초당 20건 × 60초(NFR-PRF-03), 검색 1건 = 1km + 10km |

각 경우를 DB 재시작 직후(1회차)와 메모리에 올라온 뒤(2회차) 두 번 잰다.

## 기준

검색 전체 목표는 서버 처리 p95 ≤ 300ms(NFR-PRF-01)다. 임베딩 서버(p95 94ms)·BM25·순위 계산이 같이 들어가므로 **DB 쿼리 하나는 p95 ≤ 150ms**를 목표로 본다.

넘는 경우가 있으면 차례로: ① 병렬 쿼리(`max_parallel_workers_per_gather`) ② 앱 메모리에 벡터를 올려 범위 안만 계산 ③ 넓은 범위에만 HNSW(근사라 이식 검증을 다시 함).

가장 무거운 경우(질의 'GS25'): 시도 전체(48,440곳) p50 551 / p95 963ms, 서울 가장 빽빽한 곳 10km(21,465곳) p50 310 / p95 499ms.

동시 부하(초당 20건 × 60초, 검색 1건 = 1km + 10km): 1,200건 오류 0, **p50 4,699 / p95 8,986ms**. 처리량을 못 따라가 대기열이 쌓였다.

### 원인: 벡터를 TOAST에서 꺼내는 비용

시도 전체 쿼리의 EXPLAIN(요약):

```
Parallel Bitmap Heap Scan on store_snapshot_v1  rows=16147 × 3 프로세스
  Heap Blocks: exact=4660
  Buffers: shared hit=432,304          ← 전부 메모리, 그런데 행당 약 9페이지
  Bitmap Index Scan on ix_store_snapshot_v1_code  rows=48440  11ms
Execution Time: 958ms
```

- `embedding`은 `vector(1024)` = 약 4KB라 행 안에 못 들어가고 TOAST(별도 저장소)에 나뉘어 있다. 본 행은 4,660페이지(페이지당 약 10행)에 있지만, 벡터를 꺼낼 때마다 TOAST 색인과 조각 페이지를 읽어 **행당 약 9번 버퍼를 읽는다**(432,304 ÷ 48,440).
- 그래서 행 하나에 약 50µs가 든다. 1024차원 내적 계산 자체는 1µs 안팎이니, 시간 대부분은 계산이 아니라 TOAST에서 벡터를 꺼내는 데 쓴다.
- 범위로 먼저 거르는 방식 자체는 잘 동작한다(코드 색인 11ms). **범위 안이 수만 곳이 되는 경우에만** 느리다.

### 판단

- **HNSW는 아직 도입하지 않는다.** 원인이 "계산할 행이 많아서"보다 "행마다 벡터를 꺼내는 비용"에 있다. 이걸 먼저 줄이면 근사 검색(정확도 손실, 이식 검증 다시 함) 없이 기준 안에 들어올 가능성이 크다.
- 다음 측정(2차)에서 같은 질의로 비교할 것:
  1. **벡터를 행 안에 저장**: `ALTER COLUMN embedding SET STORAGE PLAIN` 후 테이블을 다시 쓴다. 페이지당 1행이라 힙이 약 1.8GB로 커진다.
  2. **halfvec(1024)**(16비트, 약 2KB) + `STORAGE PLAIN`: 페이지당 3행, 힙 약 0.6GB. 순위가 바뀌는지 평가 질의로 확인해야 한다.
  3. 남는 초과분은 확장 단계를 넓은 범위(10km·시도)로 바로 가지 않게 하는 쪽(검색 설계)이나 앱 메모리 계산(기준의 ②)으로 본다.
- 2차 노트북: [`infra/colab/db_storage_bench_2.ipynb`](../../infra/colab/db_storage_bench_2.ipynb). 같은 덤프·질의로 `base`(지금) / `plain` / `half` 세 표를 만들어 크기, 경우별 p50·p95, halfvec 순위 일치율(반경 10km·시군구 상위 10·50), 가장 무거운 경우와 EXPLAIN, 동시 부하를 표마다 잰다. Drive 준비물은 1차와 같고 약 35~45분 걸린다. 결과는 `service_load/bench/db_storage_<시각>.md`.
- **동시 부하**는 2 CPU에서 10km 쿼리 하나가 병렬 프로세스 3개로 약 110ms씩 CPU를 쓰므로 초당 20건을 처리할 수 없다. 위 1·2로 쿼리당 CPU가 줄어든 뒤 다시 잰다. 그래도 모자라면 운영 DB의 CPU 수(최소 4개)를 요구사항으로 적는다.

세 경우 모두 대기열이 쌓였다. 다만 이 측정은 부하를 만드는 클라이언트(Python 스레드 32개)도 같은 CPU 2개를 쓰고, 모든 검색이 10km까지 넓어지는 최악의 경우라 서버 처리량을 판단하기엔 부족하다.

### 판단(2차)

- **벡터는 행 안에 저장한다(TOAST 쓰지 않음).** plain·half 모두 base보다 3~5배 빠르고, 시도 전체를 빼면 모든 경우가 기준 안에 든다. **HNSW는 넣지 않는다.**
- 남은 선택: 어떤 형으로 저장하나.
  - **plain(fp32)**: 결과가 지금과 똑같아 이식 검증을 다시 할 필요가 없다. 대신 시도 전체 p95 170ms로 기준을 조금 넘고, 버전 하나가 1.84GB라 갱신 중 두 버전이 있으면 shared_buffers 2GB를 넘는다.
  - **half(16비트)만**: 가장 빠르고 작지만 순위가 조금 바뀌어 이식 검증을 다시 해야 한다.
  - **half로 상위 100을 고르고 fp32로 다시 정렬**: half로 넓게 훑은 뒤 100곳만 TOAST의 fp32 벡터로 다시 계산한다. 상위 50 겹침이 99.97%라 결과는 사실상 fp32와 같을 것으로 보이며, 메모리에 올릴 부분은 0.6GB다. 3차에서 쿼리 속도와 fp32 결과 일치율을 확인해야 한다.
- 시도 전체에서 half가 읽은 페이지(38,863)가 행 수(48,440)에 가깝다. 같은 시도의 가게가 여러 페이지에 흩어져 있다는 뜻이라, 적재할 때 법정동 코드 순으로 넣으면 읽는 페이지를 더 줄일 수 있다(적재 코드에서 정렬만 하면 됨).
- 동시 부하: 운영 DB는 **CPU 4개 이상**을 요구사항으로 적고, 실제 서버에서 클라이언트를 따로 두고 다시 잰다.
- 3차 노트북: [`infra/colab/db_rerank_bench_3.ipynb`](../../infra/colab/db_rerank_bench_3.ipynb). 표 네 개를 비교한다.
  - `plain`: fp32를 행 안에(기준).
  - `plain_sorted`: plain과 같되 법정동 코드 순으로 넣음.
  - `rr`: halfvec(행 안) + fp32(TOAST). halfvec로 상위 100을 고른 뒤 fp32로 상위 50을 다시 정렬.
  - `rr_sorted`: rr과 같되 법정동 코드 순으로 넣음.
  - 경우마다 질의 전부의 상위 50을 plain과 가게·순서까지 비교하고, 다르면 처음 달라진 순위와 점수를 적는다(동점이면 순서만 바뀐 것).
  - 결과는 `service_load/bench/db_rerank_<시각>.md`. 약 40~50분 걸린다.

가장 무거운 경우(p95): 시도 전체(48,440곳) plain 181 / plain_sorted 135 / rr 111 / **rr_sorted 74ms**, 서울 가장 빽빽한 곳 10km plain 105 / plain_sorted 98 / rr 107 / **rr_sorted 90ms**.

- 반경 1km p95가 2차(plain 14ms)와 달리 크게 흔들렸다(plain 186). p50은 3~20ms로 작아, 표를 메모리에 올린 직후 처음 재는 경우라 생긴 흔들림으로 보인다. 4차는 한 번 데운 뒤 잰다.
- 동시 부하는 넷 다 대기열이 쌓였다(p95 2.8~3.4초). 클라이언트가 같은 CPU를 쓰므로 비교용으로만 본다.

### 결과 비교에서 찾은 것: 동점

같은 fp32인데 넣는 순서만 바꾼 `plain_sorted`도 `plain`과 상위 50 순서가 다른 질의가 있었다(반경 10km 82개, 시도 169개). 처음 달라진 자리의 점수가 **모두 같았다**. 체인점처럼 문서(`가맹점명 / 취급품목`)가 같은 가게는 벡터가 같아 점수가 같고, 쿼리에 동점 기준이 없어 저장 순서를 따랐다.

- 정책 7-5(같은 점수면 `store_id` 오름차순, [`SEARCH_HANDOFF.md`](../search/SEARCH_HANDOFF.md) 2절 10)가 [`DB_TABLES.md`](DB_TABLES.md) 10-1절 벡터 쿼리에 빠져 있다. 동점이 상위 50 경계에 걸리면 **어느 가게가 후보에 드는지가 저장 순서에 따라 바뀐다**. 쿼리에 `, s.store_id`를 넣어야 한다.
- 그래서 3차의 `rr` 일치율(반경 10km 상위 50 같음 524/690 등)도 동점 영향과 섞여 있어, 다시 정렬이 정확한지는 이 숫자로 판단할 수 없다.

### 판단(3차)

- **`rr_sorted`를 채택할 후보로 본다.** 모든 경우 p95가 기준 안이고(가장 무거운 시도 74ms), 메모리에 올릴 부분이 0.61GB다. 법정동 코드 순 적재는 적재 코드에서 정렬만 하면 되고 비용이 없다.
- 결과가 fp32와 같은지는 **4차에서 동점 기준을 넣고** 확인한다. 노트북 [`infra/colab/db_tiebreak_bench_4.ipynb`](../../infra/colab/db_tiebreak_bench_4.ipynb)(약 25분, 결과 `service_load/bench/db_tiebreak_<시각>.md`).
  - `plain_sorted`(fp32)와 `rr_sorted`를 같은 동점 기준으로 비교하고, 지금 파티션(`base`)과도 반경 10km·시군구를 비교한다. 모든 질의에서 상위 50 가게·순서가 같아야 통과.
- 통과하면 V1 스키마에 `embedding_half halfvec(1024)`(STORAGE PLAIN)를 추가하고, 적재를 법정동 코드 순으로 바꾸고, 10-1절 쿼리에 동점 기준과 다시 정렬을 넣는다. 통과하지 못하면 `plain_sorted`(fp32만 행 안)로 간다.
